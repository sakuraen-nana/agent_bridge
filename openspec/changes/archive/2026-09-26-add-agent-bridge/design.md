## Context

本仓库当前只有 OpenSpec 脚手架（未提交）、0 字节的 `AGENTS.md`、空的 `openspec/config.yaml` 模板，没有 `.gitignore`，也没有任何实现。实现本工具须满足的硬约束：

- **零第三方运行时依赖**：仅 Python 标准库；目标机任意 Python 3.7+ 可直接运行，不得引入 venv、pip 或联网步骤
- **自包含**：除工具自身目录外不读取任何文件——宿主项目可能提供的共享自举/工具模块一律不得依赖
- **跨平台一致**：被控端在 Linux 与 Windows 上行为一致；入口须可在任意工作目录下调用、整文件可被 Python 2 解析（误用时给出提示而非语法错误）
- **分发模型**：本仓库即交付物（GitHub）；被控机与被控方（客户端侧）各持一份目录，更新 = `git pull`
- 既有使用经验中必须保留的操作语义：多组 `token` / `host` 后者覆盖解析、token 文档取自工具自身目录、exec 的相对路径以服务器启动目录为基准、Windows cmd 转义负担、长静默不误杀
- **文档边界**：使用方的机器清单、部署拓扑、凭据位置、与具体项目的集成方式不在本仓库记录（见 D8）

## Goals / Non-Goals

**Goals:**

- 按规格实现首版：外部可观察行为以本仓库 `openspec/specs/agent-bridge/spec.md` 为准
- 良好项目结构：src 包布局（可 import、可测试）＋ 仓库根单一入口 `run.py`
- 自包含、零依赖：整目录拷到任意机器任意路径即可运行
- 仓库自足：README / AGENTS.md / openspec context / .gitignore 齐备，克隆本仓库的读者能得到全部信息

**Non-Goals:**

- 不改协议、不加功能（鉴权升级、HTTPS、命令白名单、并发策略等一律另立变更）
- 不做打包发布（PyPI、单文件 exe、安装器）；部署方式就是"目录在哪儿就在哪儿跑"
- 不在本仓库记录使用方的机器清单、部署拓扑与项目集成细节
- 不建 CI；测试以开发机上可跑为准

## Decisions

### D1. src 包布局 + 仓库根 `run.py`

`src/agent_bridge/{__init__,server,client,bootstrap}.py`，入口 `run.py` 在仓库根。理由：主体成为可 import 的包，测试直接 import；入口薄，只做解释器检测与分发。备选（未被采纳）：扁平布局（部署最直接，但测试需 sys.path 体操、无命名空间）；主体与入口同目录（无命名空间且入口与实现混放）。

### D2. 自举自带：`bootstrap.py` 最小集 + 入口内联版本检测

`bootstrap.py` 承载工具需要的自举能力（定位工具根、行缓冲设置、日志/失败辅助、跨平台控制台处理），由 `run.py` 在版本检测通过后 import（Py2 下不可解析的部分留在 `bootstrap.py` 与包内，入口文件本身保持 Py2 可解析）。备选（未被采纳）：拷贝宿主项目的共享自举模块（带其路径与语义假设，违背自包含）；入口内联全部逻辑（入口膨胀，且在 Py2 解析约束下难以维护）。

### D3. 路径解析：一律以"工具根"为基准

包内统一定位工具根（含 `run.py` 的目录，由包目录向上两级得到）；`bridge.local.md` 缺省位于工具根，与调用时工作目录无关。理由：src 布局下模块文件位置（`src/agent_bridge/`）不是工具根，必须显式区分，否则 `python -m agent_bridge.client` 与 `python run.py exec …` 会解析到不同文件。备选（未被采纳）：文档与包同目录（模板散落在 src 内，搬迁易漏）；要求调用者先 `cd`（与"任意工作目录"冲突）。

### D4. 入口分发方式：子进程调用 `python -m agent_bridge.<主体>`

`run.py` 经子进程启动 `[sys.executable, "-m", "agent_bridge.server" | "agent_bridge.client", *rest]`（PYTHONPATH 指向本仓库 `src/`），透传退出码；信息行一律走 stderr，stdout 与直调模块逐字节一致。理由：信号、stdout 缓冲与管道语义和直调完全同构，并满足"仅需任意 Python 3"。备选（未被采纳）：进程内 import 后调用 `main()`（少一层进程，但 stdout/信号语义不再同构，解释器检测的意义也被削弱）。

### D5. 行为范围冻结：只实现规格定义的行为

实现逐条对照 `spec.md`，不做任何"顺手改进"；实现中发现的改进点（含协议与工效）一律记入跟进项、另立变更。理由：首版实现的最大风险是混入未经规格确认的行为；规格是唯一行为契约。

### D6. 测试：stdlib unittest，包内起服务、临时端口

`tests/` 用 unittest（零第三方依赖，与仓库取向一致）：测试直接 import 包，把服务实例端口覆盖为临时端口（`0`）以隔离并行/残留实例；另设用例在端口空闲时验证真实默认端口行为。覆盖：token 文档解析（含多组后者覆盖）、认证负路径（无/错 token → 404）、hello 字段、exec 成功/非零退出/超时/客户端断开/长静默、download 完整性与两类错误、client 对回环实例的 scan/hello/exec/download 与退出码、入口转发的 stdout 一致与退出码透传。备选（未被采纳）：pytest（引入第三方依赖，违背仓库取向）；只留存脚本式手工自测（不可重复执行）。

### D7. 入口"可被 Python 2 解析"用静态语法扫描近似守卫

目标环境不保证有 Python 2 解释器，无法真机校验；`tests/` 内置静态扫描（f-string、`:=`、`->`、`nonlocal`、矩阵乘 `@`、数字下划线、缺 `from __future__ import print_function`）作为近似守卫，只覆盖入口文件。局限如实记入测试注释与 README：这是近似，不替代 Py2 真机解析。备选（未被采纳）：引入 py2 解释器（无外网环境不可得）；不做守卫（约定会随新改动静默漂移）。

### D8. 仓库定位与文档边界（AGENTS.md + config.yaml context）

写入本仓库自身的工作约定：**仓库定位（独立通用工具，只维护工具自身的通用事实）**、OpenSpec 工作流、单一 Python 入口约定、提交约定（委派 `.claude/skills/git-commit/SKILL.md`）、文档写法（仓库自足：不用随读取位置改变的指代）、以及"需要真机的验证"如何登记。`openspec/config.yaml` 的 context 同步填写（语言 Chinese、技术栈 Python 标准库、部署模型通用描述、行为范围冻结）。

**边界**：本仓库视作独立、纯净的工具软件——**机器清单与角色、部署拓扑与路径、凭据位置、与任何使用方项目的关联（来源、迁移史、集成方式）一律不在本仓库记录**，由其各自的仓库存储与维护；本仓库只描述工具自身的通用行为、用法与约束，需要指代运行环境时用通用描述（"被控机""客户端侧"）。本变更的 tasks 是交付工作记录，同样遵循该边界。

### D9. 部署与分发模型（通用描述）

本仓库为交付物与规范来源；被控机持一份目录并**部署于被控项目目录之外**（服务端），使用方客户端侧另持一份（客户端 + 自己的 `bridge.local.md`）；更新 = 各自 `git pull`。若某台机器访问本仓库的通道不通，可由使用方经离线/局域网传一份目录（**仅为引导手段，不改变工具设计**）。备选（未被采纳）：vendor 进被控项目（部署于项目内正是本工具要避免的形态）。

## Risks / Trade-offs

- [无外网环境导致获取/更新不便] → D9 离线/局域网引导；规范来源始终是本仓库
- [实现与规格偏离] → D5 行为范围冻结 + D6 测试覆盖 + 实现-规格逐条对照复核（tasks §2）
- [src 布局下路径解析出错（token 文档/自定位）] → D3 单一工具根规则 + 专门用例（任意工作目录、`python -m` 直调、经入口三条路径结果一致）
- [静态扫描守卫不等于 Py2 真机校验] → D7 如实记录局限；入口改动仍需人工留意该约定
- [被控机暂不可达，真机验证挂起] → 代码与测试部分先行；部署验证与交付衔接由使用方按其部署环境与节奏推进，不虚标完成
- ["仅标准库"约定被后续改动破坏] → README 与 AGENTS.md 明示；新增依赖须走提案

## Migration Plan

1. 本仓库内实现（D1–D8）：包与入口、测试、README、AGENTS.md、config context、.gitignore；脚手架与实现分提交入库
2. 客户端侧部署验证：把本仓库克隆/拷入任意非项目目录，复制模板为 `bridge.local.md`，跑回环全链路（scan → hello → exec（成功/失败/超时）→ download 哈希一致）
3. 被控机侧部署验证：在一台 Windows 被控机上把本仓库部署于被控项目目录之外，启动服务并抄录 token（首次启动的防火墙授权属人工步骤）
4. 真实跨机验证：从客户端侧经本工具对被控机执行一次真实命令、并取回一个文件校验一致
5. 交付衔接：使用方仓库自行记录"独立部署已就绪"及其后续动作；本仓库不记录

**Rollback**：本仓库为独立交付物，回滚 = 回到上一提交；被控机侧若仍有旧形态由使用方掌握，本仓库的变更不影响它。
