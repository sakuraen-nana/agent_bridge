## Why

路线图第 4/5 步。新应用已具备完整通道能力与运维形态，但设备接入仍需手工维护 `[[peer]]`——手抄 UUID 与 token 极易出错，且剪贴板片段携带的是会话 token（重启即失效）。本变更把「找到设备 → 配对 → 自动写进配置 → 一眼看到在线状态」做成图形闭环：每 3 秒局域网信标发现设备；点击发起配对、对端人工同意后自动交换长期凭据；已配对列表每 5 秒探测在线状态。

## What Changes

- **局域网发现**：固定 UDP 端口 **37778**——各实例每 3 秒向局域网广播信标（协议版本 / UUID / 短名 / 主机名 / 服务端口）并同时监听（IPv4；多私网接口时按接口网段定向广播）；收到即记入「最近活跃设备」表（含来源 IP），30 秒未再见即过期。信标**不携带任何凭据**；本机 UUID 的自播被忽略；已配对设备在列表中标记
- **图形化配对**：设备列表点击「发起配对」→ 向目标 `POST /pair/request`（**本应用唯一免 token 端点**）提交我方身份（UUID / 短名 / 服务端口，来源地址由连接取得）；目标界面弹出对话框（显示请求方 UUID / 短名 / 来源 IP），用户**同意**或**拒绝**；同意时把本机配置（UUID / 短名 / 端口 / **长期 token**）返回请求方；请求方**自动写入** `[[peer]]`（地址 = 发现到的来源 IP，防止多网卡下不可达）
- 配对请求行为：同时仅处理一条待决（另有请求返回「忙」）；请求方最长等待 120 秒；被拒 / 超时 / 忙均有明确回执；同一来源可随时重发；重配对同一 UUID 为幂等覆盖
- **已配对设备列表**：显示各 peer 的短名（含冲突标记）、UUID、地址与在线状态；每 5 秒探测一次（`/hello`，单机 2 秒超时）——状态区分 **在线** / **在线但凭据失效**（token 被重置或轮换，需重新配对）/ **离线**
- GUI：主界面新增「发现设备」与「已配对设备」两个区块；配对对话框（1 秒轮询待决请求）；在线状态每 5 秒刷新
- 规格：`agent-bridge-app` 新增「局域网发现信标」「图形化配对」「已配对设备列表与在线状态」三组要求；「服务端启动与端口」增补 UDP 监听端口（占用为独立错误、不阻断主服务）

**BREAKING**：无（新端点与端口均为增量）。

## Impact

- Rust：新增 `discovery.rs`（UDP 广播与监听、最近活跃表）、`pairing.rs`（免 token 端点处理、待决请求与一次性决定通道、出站配对客户端）、`config::add_peer`（幂等写入 `[[peer]]`）、并发 hello 探测；复用既有 reqwest/tokio，无新增第三方依赖
- Flutter：发现列表、配对对话框（轮询待决 + 同意/拒绝）、已配对列表（5 秒定时器）；widget/集成测试扩展
- 安全模型：**唯一免 token 端点**只把「某人请求配对」事件呈现给使用者，凭据仅在**人工同意**后返回且只回给请求方；信标无凭据；请求方来源 IP 由 TCP 连接取得并展示（供人判断）；README 安全声明增补
- 验证：Linux 本机双实例端到端（不同数据目录与端口；同机 UDP 广播可互见）——发现、同意/拒绝/超时/忙、自动写入后 CLI 连通、在线三态、信标过期；Windows 双机进验收
